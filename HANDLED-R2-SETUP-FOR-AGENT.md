# Handled intake — Cloudflare setup

**Addressed to: an AI coding agent with admin access to the Cloudflare account
behind shanegring.com.** Shane has been asked to hand you this file.

Everything below is one job: make the Handled client intake work in production.
The code is written, tested and merged-or-mergeable; it does nothing today
because it has no storage. Roughly fifteen minutes of work, most of it
automatable from the CLI.

---

## Read this before running anything

Two ways to do this job cause real damage. Both look like the obvious approach.

### 1. Do NOT add a `wrangler.toml` or `wrangler.jsonc` to the repo root

Declaring these bindings in a config file is the natural instinct. It will take
the live site down.

Cloudflare's docs are explicit: once a Pages project has a Wrangler config file,
*that file becomes the source of truth* and the dashboard becomes read-only for
bindings. The `shanegring-com` project has bindings configured in the dashboard
that are written down **nowhere in the repo** — at minimum `SCAN_KV`,
`ANTHROPIC_API_KEY`, `ATTIO_API_KEY`, `LEAD_SHEET_URL`, `BEEHIIV_API_KEY`,
`TALLY_SIGNING_SECRET`, `CAL_WEBHOOK_SECRET`, `RB2B_WEBHOOK_SECRET`. A config
file declaring only the Handled bindings would remove the rest, breaking the
Scan, the newsletter signup and every webhook receiver on the site.

(`mcp/wrangler.jsonc` exists in the repo. That is a **separate Worker** with its
own deploy. It is not precedent for this.)

### 2. Do NOT PATCH `deployment_configs` without reading it first

Adding the R2 binding needs the Pages API, and `deployment_configs.production`
is replaced wholesale by what you send. Sending only `r2_buckets` removes every
other binding — the same outage as above by a different route.

**GET the project, merge your addition into the existing config, PATCH the
merged result.** Verify afterwards that the bindings you did not touch are still
listed.

## Step 1 — Create the bucket

```bash
npx wrangler@4 r2 bucket create handled-intake
npx wrangler@4 r2 bucket list        # confirm it is there
```

Do not enable public access (`r2.dev`). Files are served through short-lived
signed links generated by `functions/api/handled/file.js`; the bucket itself
stays private.

## Step 2 — CORS on the bucket

**This step is invisible when skipped and breaks every upload.** The browser
PUTs directly to R2 cross-origin and sets a `Content-Type` header, which forces
a preflight. No CORS policy means every file and every recording fails with an
opaque network error, while the rest of the intake looks perfectly healthy.

```bash
cat > /tmp/handled-cors.json <<'JSON'
[
  {
    "AllowedOrigins": ["https://shanegring.com", "https://www.shanegring.com"],
    "AllowedMethods": ["PUT"],
    "AllowedHeaders": ["content-type"],
    "MaxAgeSeconds": 3600
  }
]
JSON

npx wrangler@4 r2 bucket cors set handled-intake --file /tmp/handled-cors.json
npx wrangler@4 r2 bucket cors list handled-intake
```

## Step 3 — Bind the bucket to the Pages project

No `wrangler pages` subcommand manages bindings, so this is the API — and it is
the step warning 2 is about.

```bash
ACCOUNT="$CLOUDFLARE_ACCOUNT_ID"
PROJECT="shanegring-com"
AUTH="Authorization: Bearer $CLOUDFLARE_API_TOKEN"

# READ the current production config first.
curl -s -H "$AUTH" \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT/pages/projects/$PROJECT" \
  | jq '.result.deployment_configs.production' > /tmp/prod-config.json

# Inspect it. Note every binding already present — you must not lose any.
cat /tmp/prod-config.json

# MERGE the new binding into what is already there.
jq '.r2_buckets = ((.r2_buckets // {}) + {"HANDLED_BUCKET": {"name": "handled-intake"}})' \
  /tmp/prod-config.json > /tmp/prod-config-new.json

# Diff the two before sending. This is the moment to catch a mistake.
diff <(jq -S . /tmp/prod-config.json) <(jq -S . /tmp/prod-config-new.json)

# PATCH the merged config.
curl -s -X PATCH -H "$AUTH" -H "Content-Type: application/json" \
  "https://api.cloudflare.com/client/v4/accounts/$ACCOUNT/pages/projects/$PROJECT" \
  --data "$(jq -n --slurpfile p /tmp/prod-config-new.json \
            '{deployment_configs: {production: $p[0]}}')" | jq '.success, .errors'
```

The binding variable name must be exactly **`HANDLED_BUCKET`** — the code looks
it up by that name.

Note: the API represents bindings as an object keyed by variable name, while
Wrangler config files use an array of `{binding, bucket_name}`. Read the config
you actually got back and match its shape rather than trusting either form.

**After patching, re-read the project and confirm every binding that was there
before is still there.**

## Step 4 — Create an S3 API token  *(dashboard — no CLI path)*

Presigned uploads need S3 credentials. I could not find a documented
wrangler or API route that returns an S3 access key pair, so this one is manual:

**R2 → Manage R2 API Tokens → Create API token**

- Permissions: **Object Read & Write**
- Scope: the `handled-intake` bucket only
- Copy the **Access Key ID** and **Secret Access Key** — the secret is shown once

If you do find an API path for this, use it; just make sure the result is a
bucket-scoped Object Read & Write credential.

## Step 5 — Six secrets

```bash
P="--project-name=shanegring-com"

echo -n "<account id>"            | npx wrangler@4 pages secret put R2_ACCOUNT_ID $P
echo -n "<access key id>"         | npx wrangler@4 pages secret put R2_ACCESS_KEY_ID $P
echo -n "<secret access key>"     | npx wrangler@4 pages secret put R2_SECRET_ACCESS_KEY $P
echo -n "handled-intake"          | npx wrangler@4 pages secret put R2_BUCKET $P

# Two fresh random strings — generate, do not invent.
node -e 'console.log([...crypto.getRandomValues(new Uint8Array(24))].map(b=>b.toString(16).padStart(2,"0")).join(""))'

echo -n "<first random string>"   | npx wrangler@4 pages secret put HANDLED_ADMIN_SECRET $P
echo -n "<second random string>"  | npx wrangler@4 pages secret put HANDLED_DOWNLOAD_SECRET $P

npx wrangler@4 pages secret list $P
```

`HANDLED_ADMIN_SECRET` is needed to issue client links — **give it to Shane, and
ask him to pass it to Chris.** Nobody can send a client an intake link without
it. `HANDLED_DOWNLOAD_SECRET` signs the file links in Shane's email and is not
needed by anyone outside Cloudflare.

## Step 6 — Redeploy

Bindings and secrets only take effect on a **new** deployment.

```bash
npx wrangler@4 pages deployment list $P | head -5
```

Then either retry the latest deployment from the dashboard, or push any commit
to `main` (the repo auto-deploys on push to `main`).

## Verify

```bash
curl -s "https://shanegring.com/api/handled/session" -H "X-Handled-Token: nope"
```

| Response | Meaning |
|---|---|
| `{"error":"The intake isn't configured yet."}` | Bucket binding not live. Check the variable name is `HANDLED_BUCKET`, and that you redeployed. |
| `{"error":"invalid_link"}` | **Correct.** Storage is working — the token is deliberately fake. |

Then the end-to-end check, which is the only one that tests CORS and presigning:

1. Ask Chris for an intake link (he issues it with `HANDLED_ADMIN_SECRET`).
2. Open it, fill in the four required fields, upload any image.
3. Watch the Network tab: an `OPTIONS` returning 200, then a `PUT` returning
   200, straight to `*.r2.cloudflarestorage.com`.

A PUT reported as a CORS error means step 2's origins do not match exactly. A
403 or 401 on the PUT means the S3 credentials in step 5 are wrong or not
scoped to this bucket.
